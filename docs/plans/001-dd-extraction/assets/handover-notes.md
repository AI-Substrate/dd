# Handover notes — wire format & renderer authority

**Owner**: plan 001 (dd extraction) · **Audience**: whoever swaps `harness dd …` for the `dd`
binary downstream (pij-related-koala) · **Written**: phase 3, tk-0003.

This file collects the facts a consumer needs that are **not** visible from the package itself.
Phase 4 folds it into the handover packet; it is written here, at the moment of the change, so
it records what was measured rather than what was later remembered.

---

## 1. The generated banner changed, and that is a wire format

Every `.dd.md` this package renders opens with a generated-file banner. Upstream
(`harness-engineering`) emits:

```
<!-- GENERATED by `harness dd build` — do not hand-edit; regenerate from the .dd.json. -->
```

This package emits:

```
<!-- GENERATED by `dd build` — do not hand-edit; regenerate from the .dd.json. -->
```

**The change is deliberate** (plan 001 tk-0003, ruled 2026-08-07). The banner names the command
that regenerates the file, and in this package that command is `dd build` — the binary IS `dd`.
A banner telling a reader to run `harness dd build` is an instruction that does not work here.

**What this means for a consumer.** The banner is the first line of every generated sibling, so
it is effectively a wire format: two renderers that disagree on it produce byte-different output
from byte-identical input.

- **Expect a one-line diff on every `.dd.md` in the repository the first time you regenerate
  after swapping binaries.** That is the whole diff. It is not drift, not data loss, and not a
  renderer regression.
- **Per-package banners are self-consistent**, and that is the intended end state. Each package
  tells the truth about its own command surface. Do **not** try to make the two repositories
  agree by pinning one to the other's string — that would put a wrong instruction in one of them
  permanently.
- **Adjudication rule** for a suspected drift: run the LOCAL `dd build --check`. Green locally
  plus a banner-only diff = renderer skew, expected. Anything beyond the banner line = real
  drift, investigate it. Note the narrow scope this actually has — see the correction below:
  `harness plan validate` never reports drift at all, so the only harness command that can raise
  a banner false-positive is `harness dd build --check`, which the authority split forbids.

## 2. Renderer authority split (in force from the tk-0003 landing commit)

Quoted from `plan.dd.md#risks` (o-prime, 2026-08-07), because this is the binding form:

> RENDERER AUTHORITY SPLIT (o-prime 2026-08-07, from the tk-0003 banner collision): from the
> tk-0003 landing commit onward, THIS repo documents are mutated/rendered ONLY by the LOCAL dd
> bin (set/add/rm/build) — upstream harness dd set/build on them is forbidden (its renderer
> silently regresses the banner). harness plan validate REMAINS the semantic authority
> (checks/gates/contradictions, per Jordan: plan checks stay harness-side); drift authority is
> LOCAL dd build --check. A harness-reported drift is adjudicated: local check green +
> banner-only diff = renderer skew (expected until koala swaps upstream), anything else = real.
> Window closes at handover.

The plan is append-only, and a later row narrows this one. Quoted from the same source
(`plan.dd.md#risks`, o-prime `b479372`):

> CORRECTION to the renderer-authority guardrail (measured by the PM): harness plan validate is
> NOT drift-affected — drift comparison is build alone. Blast radius of the banner skew =
> upstream write path + upstream dd build --check (E422 false-fail). The authority split stands;
> the harness-drift adjudication clause in the earlier row describes a case that cannot occur and
> is superseded here (append-only, prior row retained).

So: the split itself is unchanged, and the blast radius is **narrower** than the original wording
implies. Read the two together — the second is the operative scope.

### Measured behaviour behind that ruling

Probed 2026-08-07 against this repository at commit `13d86f8`, upstream basis `d08f4942`. Every
row is an observation, not an inference; the write-path rows were probed on a throwaway copy and
reverted. Re-derive any row by running the command in its cell against a locally-generated
sibling and diffing the first line.

| Command | Effect on a locally-generated sibling | Severity |
|---|---|---|
| `harness dd set` / `add` / `rm` | **Silently rewrites the banner to the upstream string.** Envelope reports `status: ok`. | **Silent regression — the dangerous one** |
| `harness dd build <doc>` (write mode) | Same renderer, same silent regression. | Silent regression |
| `harness dd link verify-basis --update` | Regenerates a sibling; inherits the same regression. | Silent regression |
| `harness dd build --check <doc>` | Reports `status: error`, `E422` (drift) on a file that is not drifted. | False failure |
| `harness dd validate <doc>` | `status: ok`, 0 issues. Validation does not compare the sibling. | **Unaffected** |
| `harness plan validate … --address …#tasks` | `status: degraded`, exit 0, **0 errors**, zero drift-class findings. | **Unaffected** |
| local `dd build --check <doc>` | `status: ok`, `drift: false`. The control. | Authority |

The two `Unaffected` rows are the load-bearing ones: they are why `harness plan validate` stays
the semantic authority and why the split is narrow rather than a fork. They were measured, not
assumed.

### Why the silent case matters more than the loud one

`build --check` failing loudly is survivable — somebody sees it. `dd set` returning `ok` while
regressing the banner is not: the damage lands in a commit nobody inspected, and the next
`--check` blames whoever touched the file last. **Any workflow that mutates this repository's
documents must use the local bin**, which after `npm run build` is:

```bash
node bin/dd.js set "<file>#<address>" <value>
node bin/dd.js build <file>
```

## 3. Closing the window

The split exists only while the two renderers disagree. It closes when the downstream consumer
swaps to this package's binary — at which point there is one renderer again and the banner
question is settled by construction. Until then the rule is: **local bin writes, harness
validates.**

## 4. Regenerating every sibling from scratch

If a swap or a merge leaves banners mixed, this restores the whole repository to one renderer:

```bash
cd /Users/jordanknight/substrate/dd
npm run build
node bin/dd.js build docs/plans/001-dd-extraction/plan.dd.json
node bin/dd.js build docs/plans/001-dd-extraction/execution-log.dd.json
for phase in 1 2 3 4; do
  node bin/dd.js build "docs/plans/001-dd-extraction/assets/tasks/phase-${phase}/tasks.dd.json"
done
```

The render-fixture goldens under `test/services/dd/render/fixtures/` carry the banner too. They
are not regenerated by a switch (the corpus is a spec, not a snapshot — `dd build` ships no
`--update-goldens` escape hatch, and a test pins that absence). They are proven instead: the
renderer suite compares them byte-for-byte, so a wrong banner in a golden is a red test.

## 5. The guard that keeps this true

`test/acts/binary-name.test.ts` is the ratchet. It asserts, mechanically:

- every surviving `harness dd` in `src/` sits on a **comment** line, and the per-file counts match
  an explicit allow-list of upstream-provenance mentions;
- no invocation of the shipped bin emits `harness dd`, in **either** output mode;
- the baked `dd docs` corpus contains none;
- `RENDER_BANNER` names `dd build`.

It was mutation-tested when written: reverting a single `next_action` string reddened both the
source half and the runtime half.
